# Methodology — how a case becomes a verified comparison

## Case lifecycle

```
prompt library (MIT, attributed)
        │  verbatim copy + sha256 freeze          ── cases/<id>/prompt.txt
        ▼
QWEN RUN (local, reproducible)                    ── gallery/qwen/<id>.{png,run.json}
        │  one image, fixed seed, full telemetry
        ▼
OPEN_CHALLENGE  (GPT side honestly empty)
        │  contributor BYOK run + evidence
        ▼
COMMUNITY_SUBMITTED (in review)
        │  maintainer review vs the standard below
        ▼
REVIEWED_COMPARISON   ── or REJECTED (archived with reason)
```

Any stage can instead be `BLOCKED` (technical, licensing, or rights issue)
with a recorded reason.

## The Qwen side (what "real" means here)

Every Qwen image in this repo satisfies all of the following, machine-checked
by `tools/validate_gallery.py` on every PR:

1. Generated by the committed driver against a pinned stack: engine
   `qwen-image-rocm` at a recorded commit, ComfyUI at a recorded commit,
   weights `Comfy-Org/Qwen-Image-2.1@aacf31a6` (sha256-verified per file by
   the engine's pin table).
2. Quality profile only for gallery images: bf16 DiT/TE/VAE, 40 steps,
   cfg 1.0, euler/simple, fixed seed, `--disable-smart-memory`, SDPA math.
   Fast-mode variants, if ever added, are labeled variants — a Fast image can
   never be labeled Quality (this rule exists because the engine repo's
   owner verdict rejected the int8-TE triple on typography grounds).
3. Prompt bytes sha256-verified against the frozen manifest **before** the
   request is sent; the driver aborts on drift.
4. Output PNG dimensions asserted equal to the planned canvas (IHDR parse).
5. Run record embeds: per-node websocket timing (text encode, KSampler, VAE
   decode), per-step times, sampled VRAM peak, GPU identity from
   `/system_stats`, wall time, image sha256, UTC timestamps.
6. One image per case at the pre-declared seed. No seed hunting, no rerolls;
   failures are recorded as failures and the case shows as failed.

Known limitation, stated openly: non-square canvases were unproven on this
GPU stack before this project; all 9 non-square runs here are labeled
`non_square_probe` in their records (all succeeded at ≤ ~1.05 MP).

## The GPT side (evidence tiers)

Contributors run `tools/generate_gpt.py` with **their own key** (pinned model
`gpt-image-2-2026-04-21`, default size = the case's exact canvas, default
quality `medium`, `n=1`, cost gate before any paid call). Submission evidence
determines the tier displayed:

| Tier | Evidence | Display |
|---|---|---|
| **API-evidenced** | `run.json` with the API `usage` object + request id from the CLI | green chip |
| **Self-reported** | credible statement of method (e.g. ChatGPT web UI) without an API record | labeled as self-reported |
| Not accepted | bare image, no origin statement | rejected at intake |

Review checks (maintainer, human): prompt sha256 matches the frozen case;
declared model/snapshot/size/quality are consistent with the image's
dimensions and the record; usage/request-id present for API tier; rights
declaration checked; duplicate image sha256 across submissions rejected.

**Model identity is never inferred from visual similarity.** A perfect-looking
GPT-style image with no evidence stays self-reported or gets rejected; it is
never promoted on looks.

## Fairness notes

- Same prompt bytes for both models (frozen file is the single source).
- Same canvas where the API allows: gpt-image-2 accepts custom 16-px-multiple
  sizes, so the default GPT size equals the Qwen canvas exactly (e.g.
  720×1280). Overrides are recorded in the run record.
- No negative prompt tricks on the Qwen side (empty negative, matching the
  official Qwen-Image-2.1 template); no prompt rewriting for either side.
- Temperature/seed parity is impossible across the two APIs (GPT Image 2 has
  no seed) — recorded honestly as `seed: null` on the GPT side.

## Automated validation (every PR)

`tests/test_gallery_integrity.py` + `tools/validate_gallery.py`:
case schema → prompt sha256 recompute → image sha256 recompute → PNG
dimensions vs canvas → model/weights pins present → provenance chain present →
duplicate prompt/image detection → secret scan across all tracked text files →
site-data image paths exist → status-vs-evidence consistency. CI then builds
the site (`npm ci && npm run build`) — typecheck + production build must pass.

## What this project does NOT claim

- No leaderboard, ranking, score, vote count, or "winner". The comparisons
  exist for humans to look at and judge.
- No end-to-end OpenAI API validation from the project itself (it holds no
  key). The BYOK path is verified by contract tests + recorded community runs.
- No affiliation with OpenAI, Alibaba/Qwen, or AMD.
